# vm-acme Clean Architecture Starter

This .NET 10 starter uses DDD, Clean Architecture, MediatR, Result objects and FastEndpoints. Its owner-scoped Todo example is adapted from [GeorgeLeithead/CleanArchitecture/net8](https://github.com/GeorgeLeithead/CleanArchitecture/tree/main/net8). The API runs with in-memory storage by default; PostgreSQL and SQL Server are optional.

Run `./init.ps1` on PowerShell or `bash init.sh` in Bash. The initializer prompts for a project or repository name (`acme` by default), validates it before edits, then replaces the template names before restoring/building. `./init.ps1 -Name vm-order-service` or `bash init.sh vm-order-service` produces `VmOrderService.*` namespaces/projects, deployment `vm-order-service`, environment prefix `VM_ORDER_SERVICE`, metric prefix `vm_order_service`, and solution `vm-orderservice.slnx`. A leading `vm-` is removed once when deriving names. Underscores remain in .NET identifiers while deployment, environment, and metric names use the appropriate separators. This is a one-time rename; press Enter to keep `vm-acme`.

When created from the GitHub template, `.github/workflows/template-bootstrap.yml` attempts initialization on the first push and also supports **Actions → Initialize repository from template → Run workflow**. It derives names from the repository name, runs restore/build/test and Helm lint before committing the result, and records `.template-initialized` so reruns do nothing. The immutable source repository ID is excluded. GitHub does not document a dedicated repository-created-from-template Actions event, and template workflow availability can depend on repository Actions settings; the push trigger is therefore a best-effort automatic path. Verify it in a newly created repository and use `workflow_dispatch` if no run appears. Local wrappers remain available.

Run `./scripts/setup-local.ps1` once to generate a signing key in .NET user secrets, then start the API with `dotnet run --project src/VmAcme.WebApi`. Register at `POST /api/users/register`, log in at `POST /api/users/login`, then send the returned `accessToken` as a Bearer token to `/api/todos`. The [HTTP example](src/VmAcme.WebApi/VmAcme.WebApi.http) covers the full flow. Todos support create, list, get, complete and delete, scoped to the authenticated owner. `GET /api/users/{id}` requires the server-resolved `users:read` permission and returns your own profile. See [design, errors and authorization](docs/reference-todo.md).

JWT settings: `Authentication:Jwt:Issuer`, `Audience`, `SigningKey`, `ExpirationMinutes` (default 60, range 1–1440). Development uses a local-only key; deployments supply a secret. Tokens validate signature, algorithm, issuer, audience, lifetime and registered GUID subject. Passwords use ASP.NET Identity hashing. In-memory accounts and Todos reset when the process restarts.

`/health`, `/ready`, `/version` and `/metrics` remain anonymous. Structured JSON logs go to stdout for Kibana. OpenTelemetry exports HTTP traces/metrics, SQL Server and PostgreSQL command traces and sanitized EF command duration metrics to an OTLP collector configured through `OTEL_EXPORTER_OTLP_ENDPOINT`. The existing Prometheus endpoint retains the sample MediatR/process counters for compatibility; it does not expose the OTLP histograms.

`Persistence:Provider` is required outside local settings. Explicit `InMemory` is accepted only in Development or Testing. Relational providers use a pooled context factory and at most three transient retries; repository contexts remain scoped. Compose requires a randomly generated `VM_ACME_LOCAL_JWT_KEY` supplied through the environment or ignored `.env` file. Company Helm values require Key Vault mode; see [hardening and company prerequisites](docs/template-hardening.md).

Run `dotnet test vm-acme.slnx` for unit, API, migration-model and architecture tests. Live database tests are opt-in: `./scripts/test-databases.ps1` starts disposable PostgreSQL/SQL Server containers, runs the whole suite and removes the containers. Docker must be running. Architecture tests enforce layer dependencies, framework boundaries, FastEndpoints adapters and Result contracts.

Database migrations are applied separately by `tools/VmAcme.DbMigrator`. Additive migrations create `Users` and `TodoItems` for both providers. Historical `WorkItems` data and mappings remain for compatibility; `/api/work-items` is retired and data is not automatically assigned to users. Kubernetes setup: [POC-QUICKSTART.md](POC-QUICKSTART.md). Company development profile: [DEV-DEPLOYMENT.md](DEV-DEPLOYMENT.md).

See [naming and secret policy](docs/naming-secret-policy.md) for the three secret modes, precedence, file mounts, and rotation.
